# Proposal: isolated dedicated workers in archived snapshots

## Status

Approved implementation plan. The implementation branch is based directly on `origin/master`, as requested. Runtime, policy, tests, and directly affected documentation are implemented on `codex/fix/archived-dedicated-workers`; validation results are recorded in the resulting commits and handoff.

## Objective

Archived pages should be able to use dedicated Web Workers when the worker code is either:

- generated by already-running archived JavaScript as a `blob:` URL; or
- an exact resource captured in the same snapshot.

Worker execution must retain the existing replay boundary:

- no live-origin fallback;
- no access to Archive credentials or storage;
- no arbitrary network, redirect, WebSocket, WebTransport, or WebRTC egress;
- only `GET` and `HEAD` reads of manifest-authorized resources in the same snapshot;
- no Shared Workers or Service Workers;
- no relaxation of the opaque iframe origin or frontend sandbox.

The immediate compatibility target is the Three.js `DRACOLoader` snapshot `38d11d8c-78e3-4675-adab-eca246b27576`, which creates a dedicated worker from generated DRACO decoder source.

## Scope

This change is limited to snapshot replay and its security tests. It does not add a UI route, alter the public API contract, change database entities, change the manifest JSON schema, or introduce a production dependency.

No HTML mockup is required because there is no new route or view. The existing snapshot page and its `iframe sandbox="allow-scripts"` remain unchanged.

## Current behavior and reproduced failure

The baseline is pull request 8 as merged into `origin/master` at `05e057d`. Its replay path is:

```text
captured response / imported archive
  -> SnapshotDocumentNormalizer
  -> stored canonical index.html with an embedded SnapshotRuntimeShim
  -> manifest-authorized content endpoint on 127.0.0.1
  -> cross-origin iframe with sandbox="allow-scripts"
  -> browser CSP + Connection-Allowlist enforcement
```

The following behavior was verified in the running local environment on 26 October 2026:

- `http://localhost:5173/snapshots/38d11d8c-78e3-4675-adab-eca246b27576` loads the Archive shell and the archived Three.js page.
- The iframe is rendered with `sandbox="allow-scripts"` and uses the isolated content URL on `http://127.0.0.1:5200`.
- The canvas remains black instead of rendering the character scene.
- Loading the isolated content directly reproduces this error:

  ```text
  TypeError: The archived snapshot blocked this capability.
      at new value (.../content/index.html:117:86)
      at .../assets/0783b5a3...:440:20
  ```

- The failing archived asset invokes `new Worker(this.workerSourceURL)` as part of Three.js DRACO decoding.

Two independent controls currently reject that call:

1. `SnapshotRuntimeShim` replaces `Worker` and `SharedWorker` with throwing constructors.
2. The interactive document CSP declares `worker-src 'none'`.

The `ambient-light-sensor` console message is separate. Chromium does not recognize that Permissions Policy feature in the tested runtime. Removing the unsupported directive removes the warning without enabling the sensor API in the admitted Chromium execution path.

## Existing architecture relevant to the change

### Capture and normalization

`BrowserCaptureEngine` records browser responses through `CapturedResourceCollector`. JavaScript responses, binary decoder files, models, and WebAssembly can already be stored. Captured JavaScript is normalized by `JavaScriptReferenceRewriter`, and every HTML document receives `SnapshotRuntimeShim` before archived scripts execute.

The runtime shim already:

- maps exact source URLs to snapshot-local resource paths;
- rewrites Fetch and XHR reads to captured resources;
- permits only `GET` and `HEAD`;
- omits credentials and rejects redirects;
- rewrites selected element URL properties and attributes;
- blocks explicit connection APIs and form submission.

### Delivery boundary

`SnapshotContentPolicy` applies the active replay policy only on the isolated snapshot origin. Interactive documents receive:

- a path-scoped `Connection-Allowlist`;
- a path-scoped CSP;
- `sandbox allow-scripts` without `allow-same-origin`;
- credential-free CORS;
- no-referrer and no-store response controls.

Clients that do not pass `SnapshotInteractionCapabilityPolicy` receive the static policy with `script-src 'none'` and `worker-src 'none'`.

### Stored snapshot contract

The runtime shim is embedded in the immutable canonical HTML at capture time. It is not generated at response time. Consequently, changing `SnapshotRuntimeShim` affects new or explicitly re-normalized captures only; it cannot silently change an existing archived record.

## Security model for dedicated workers

The runtime shim is a compatibility layer and defense in depth. It is not trusted as the sole egress boundary. The browser-enforced CSP and `Connection-Allowlist` remain authoritative.

This distinction matters because a worker has a separate global execution context. A normal HTTP(S) worker generally uses policies supplied with the worker response, while a local-scheme worker such as `blob:` inherits the creator's policy container. Connection Allowlists similarly apply per document or worker context and are inherited by local-scheme contexts in the current Chromium model.

The implementation must preserve these invariants:

| Invariant | Enforcement |
| --- | --- |
| Dedicated worker code comes from archived bytes | Exact runtime map lookup or an in-memory `blob:` created by archived code |
| Worker creation cannot contact the live source | Network worker URLs are converted to a local `blob:` bootstrap before native construction |
| Worker egress stays inside one snapshot | Inherited `Connection-Allowlist` plus inherited CSP |
| Same-snapshot reads cannot mutate server state | Existing request boundary allows only `GET`, `HEAD`, and preflight |
| Worker reads cannot carry Archive credentials | Opaque snapshot frame, separate credential-free origin, and credential-free CORS |
| Shared Worker remains unavailable | Runtime constructor guard and destination rejection |
| Service Worker remains unavailable | CSP excludes HTTP(S) worker entry URLs, runtime registration guard, and destination rejection |
| Unsupported browsers remain static | Existing structured Chromium capability gate |

## Recommended design

### 1. Permit only `blob:` as the native worker entry scheme

For interactive documents, change the dedicated-worker CSP entry from:

```text
worker-src 'none'
```

to:

```text
worker-src blob:
```

Do not add the snapshot HTTP scope directly to `worker-src`.

The snapshot iframe deliberately has an opaque origin because it omits `allow-same-origin`. A worker script URL must otherwise be same-origin with its caller, so a direct HTTP worker URL is not a reliable way to load a captured asset from that iframe. More importantly, a directly loaded network worker has its own policy container and would require a complete worker-specific response policy. Keeping native worker entry limited to `blob:` makes inheritance of both CSP and Connection Allowlist explicit.

The non-interactive policy remains `worker-src 'none'`.

### 2. Replace the blanket `Worker` denial with a dedicated-worker adapter

Capture the native `Worker` constructor before installing capability guards. Expose a constructor-compatible adapter that accepts only:

- `blob:` URLs; or
- URLs that resolve through the exact captured-resource map.

Reject `data:`, live HTTP(S), uncaptured, malformed, and cross-snapshot inputs with the existing archived-snapshot error style.

For a `blob:` input, call the native constructor directly. This preserves common create/use/revoke patterns such as the one used by Three.js DRACO and avoids an asynchronous blob-reading race.

For an exact captured resource, create a short-lived bootstrap script as a new `Blob`, start the native worker with that bootstrap URL, and revoke only the bootstrap URL after construction. The bootstrap then loads the captured entry script:

- classic worker: native `importScripts(capturedUrl)`;
- module worker: `import(capturedUrl)` from a classic bootstrap, with messages queued until module evaluation completes. The classic entry is required by the opaque sandbox origin; the imported worker entry and its dependency graph still execute as modules.

The original `WorkerOptions` are preserved, except credentials must remain omitted where the browser exposes that option. The returned object must remain a native `Worker` instance so `postMessage`, transferable objects, events, `terminate`, and `instanceof` behavior continue to work.

Conceptually:

```text
archived page
  -> Worker(blob URL)
       -> native dedicated worker
       -> inherited CSP and Connection-Allowlist

archived page
  -> Worker(exact captured source URL)
       -> runtime map resolves snapshot asset
       -> native Worker(blob bootstrap)
       -> bootstrap imports snapshot asset
       -> inherited CSP and Connection-Allowlist
```

### 3. Install worker-context compatibility before a captured entry script

The captured-resource bootstrap should install a worker-specific subset of the existing runtime mapping before it loads the archived worker script:

- exact source-to-snapshot URL resolution;
- Fetch and XHR mapping;
- `GET` and `HEAD` restriction;
- credential omission and redirect rejection;
- `importScripts` mapping relative to the original worker source URL;
- blocking of WebSocket, EventSource, WebTransport, SharedWorker, and WebRTC APIs;
- the same dedicated-worker adapter for supported subworkers where the browser exposes `Worker` in the worker global.

This logic should be generated from a shared internal JavaScript fragment rather than maintained as two unrelated copies. The window shim and worker bootstrap have different globals and should keep separate installation functions, but they should reuse the same serialized resource map and URL-resolution contract.

Blob workers generated by the archived application cannot be synchronously inspected or rewritten without breaking standard immediate-revocation patterns. They therefore run their original bytes directly and rely on the inherited browser policies for egress containment. This is sufficient for DRACO and preserves normal Blob Worker semantics.

### 4. Keep Shared Workers and Service Workers closed

Remove only `Worker` from the current throwing-constructor list. Keep `SharedWorker` blocked.

Add an explicit best-effort guard for `navigator.serviceWorker.register` in the document shim. This remains defense in depth: the authoritative controls are that `worker-src` permits only `blob:` and the content endpoint rejects `Sec-Fetch-Dest: serviceworker`.

Extend `SnapshotContentPolicy.IsAllowedDestination` to reject `sharedworker` and `serviceworker` destinations for every manifest role. A dedicated captured worker is loaded by the bootstrap as a script/module resource, not as an HTTP worker entry, so no `worker` destination exception is needed for the recommended design.

### 5. Remove the unsupported Permissions Policy token

Remove `ambient-light-sensor=()` from `DeniedPermissions`. Retain every other currently denied feature. No permission is added, and no other directive is reformatted or reordered.

### 6. Version the normalization behavior

Change `SnapshotDocumentNormalizer.Version` from `archive-snapshot-v1` to `archive-snapshot-v2` and emit `data-archive-snapshot="v2"` for new canonical documents.

The manifest schema remains version 4 because its shape does not change. The normalizer value already exists specifically to distinguish canonicalization behavior inside that schema.

## Test strategy

### Focused unit tests

Add deterministic assertions for:

- interactive CSP contains `worker-src blob:`;
- static CSP continues to contain `worker-src 'none'`;
- CSP never permits an arbitrary origin or wildcard worker source;
- `sharedworker` and `serviceworker` destinations are rejected;
- `ambient-light-sensor` is absent while the remaining denied permissions are retained;
- normalizer version 2 is recorded and the shim precedes archived scripts;
- the generated runtime retains Shared Worker and connection API guards;
- uncaptured worker inputs fail closed.

### Chromium integration fixture

Use the repository's existing Microsoft.Playwright version and a small in-process loopback fixture. The fixture should model the real origin separation:

- viewer on `localhost`;
- snapshot content on `127.0.0.1`;
- `iframe sandbox="allow-scripts"`;
- the production `SnapshotContentPolicy` headers;
- a separate sentinel endpoint outside the snapshot allowlist.

Cover these cases:

1. A DRACO-style JavaScript Blob Worker posts a computed result to the archived page.
2. An exact captured classic worker loads through the bootstrap and can read another captured resource.
3. An exact captured module worker loads through the bootstrap and resolves a captured module dependency.
4. An uncaptured worker target throws before a live request is sent.
5. A worker attempt to Fetch, use XHR, open WebSocket/WebTransport, or establish WebRTC outside the scope fails and the sentinel receives no request.
6. A Shared Worker attempt fails.
7. A Service Worker registration attempt fails and no registration remains after the test.
8. A request without the admitted browser capability remains script- and worker-disabled.

The integration test should assert behavior through page-visible results and sentinel request counts, not only through console text.

## Existing snapshot and migration impact

Snapshot `38d11d8c-78e3-4675-adab-eca246b27576` contains the version 1 shim in its stored immutable `index.html`. API and CSP changes alone cannot remove its embedded throwing `Worker` constructor.

The recommended implementation does not mutate that archived record. Acceptance should create a fresh version 2 capture of the same source. This preserves the project's immutable-record model and keeps the change small.

If the existing UUID itself must become executable, that is a separate storage migration decision. It would require reintroducing a bounded generation migration with hashing, validation, activation, rollback, and cleanup rather than editing the stored object in place. That work is intentionally excluded until explicitly requested and approved.

## Alternatives considered

### Allow `worker-src blob: <snapshot-scope>` and expose the native constructor

Rejected as the primary design. It fixes the current DRACO Blob Worker, but captured network workers remain unreliable from an opaque-origin iframe. A network worker also receives an independent policy container, so merely allowing the URL is not enough to preserve network containment.

### Permit only Blob Workers

Viable as a smaller fix for the current Three.js snapshot, but incomplete for pages that create workers from captured script files. The stated archive-completeness goal warrants exact captured-resource support in the same change.

### Add `allow-same-origin` to the iframe

Rejected. It would remove a core isolation property, enable origin-backed storage and cookie behavior, and let same-origin content weaken its own sandbox relationship.

### Serve archived workers from their original origins

Rejected. It would require live network access and violate deterministic, offline replay.

### Move all snapshot execution into a remote browser

Out of scope. It changes the product architecture, operating cost, and interaction model to solve a compatibility issue that can be addressed inside the existing browser boundary.

## Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| A Worker becomes a new egress channel | Require inherited Connection Allowlist and CSP in browser integration tests; do not rely on shim overrides alone |
| A captured worker URL bypasses exact resource authorization | Resolve only through the frozen manifest-derived map and keep content endpoint authorization unchanged |
| Shared/Service Worker accidentally becomes enabled by CSP | Permit only `blob:` worker entry, keep runtime guards, reject their fetch destinations, and test both APIs |
| Wrapper changes native Worker semantics | Return a native Worker object, preserve options and events, and cover transferable messages and termination |
| Blob bootstrap leaks object URLs | Revoke Archive-created bootstrap URLs after native construction; never revoke application-owned URLs |
| Worker code depends on its exact `self.location` | Blob workers retain their own Blob URL; captured-resource workers see the bootstrap Blob URL. Document this unavoidable compatibility limit and rely on URL mapping for supported relative reads |
| Browser behavior changes | Keep the existing minimum Chromium capability gate and exercise the policy in real Chromium rather than only string tests |
| Old snapshots appear fixed but still contain v1 | Record `archive-snapshot-v2`, create a fresh acceptance capture, and state migration behavior explicitly |
